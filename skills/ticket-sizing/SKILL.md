# Ticket Sizing

主动预测逐票 token 需求，结合独立验收与依赖边界确定粒度。拆票流程的 owner 是 `to-tickets`。
delivery-pipeline 的 to-tickets 阶段必须执行本 skill，并保留逐票判定产物供 tickets gate 回读；
既有票复用仍须有这份证据，不另设 coordinator 粒度复审。

## 执行步骤

1. 读取 Spec、候选票、依赖和相关代码，逐票明确验收目标、单个 Execution Worktree 的
   交付边界、需加载的代码与测试、验证路径和主要未知项。完成条件：每票均有具体范围与证据坐标。
2. 每张候选票必须主动给出 token 预测，按下节估算并填写逐票表；用户无需追加提醒。
   完成条件：每票都有数值区间、分项依据、假设和置信度，包括缺少历史运行数据的票。
3. 按粒度判据保留、拆分或合并；范围变化后重新估算最终票，合并票按共享上下文去重。
   完成条件：最终每票均有预测、判定理由、独立验收与显式依赖，超预算项有处理建议。
4. 保存逐票表并向用户展示。最终回复也必须展示逐票预测，不能仅链接产物。
   完成条件：用户在批准拆票前能看到每票预测区间、执行预算与主要不确定性。

## Token 预测

这里要求的是事前工程估算，统一标注“推断”，不是运行后的精确计量。
预测区间不能用 Unknown 代替；缺少证据时基于明确的范围假设给出更宽区间和低置信度，
列出待核验项。若范围尚未确定，给出条件式预测（“假设只覆盖 X，则为 L–U tokens”），
并将粒度结论标为待补充范围。

- **上下文峰值预测**：估算执行期间需同时保留的指令/规格、相关代码/测试、
  实现与调试对话/工具输出的 tokens；逐项给出数值区间和依据，按可能同时在场的阶段合计，
  共享内容计一次。依据来自预计读取范围、内容量、修改复杂度和验证/返工路径。
- **执行预算**：在峰值上界之上加入明确数值的余量，说明余量对应的风险；
  此处预算指建议预留的上下文容量。累计消耗不等于同时占用的上下文；
  用户另需费用或累计输入/输出消耗预测时，单列口径，不据累计消耗直接计算票数。
- **校准与容量**：相近任务的实测记录用于修正预测；没有实测记录时，仅“实测校准”记 Unknown。
  当前模型/宿主的可用上下文容量有证据才填写，无证据记 Unknown，并将容量适配标为待核验；
  token 预测照常交付。容量已知时比较执行预算，超出则沿验收边界拆分或收窄读取与验证范围后重估。
  数值按证据精度取整，不套统一前后端系数或固定模型阈值。

逐票产物格式（可用同字段列表）：

| 票 | 验收目标 / 依赖 | 上下文峰值预测（tokens） | 执行预算（tokens） | 分项依据 / 假设 / 置信度 | 实测校准 / 可用容量 | 保留、拆分或合并及理由 |
| --- | --- | --- | --- | --- | --- | --- |

## 委派评估

`to-tickets` owner 可将逐票评估委派给只读子代理，传入本 skill 绝对路径、Spec、候选票与依赖、
相关代码证据；子代理按上述逐票产物格式返回完整评估。owner 核验并保存产物，
仍由 owner 向用户展示拆分、取得批准并发布。评估必做，委派可选；模型与并发按宿主合同核验。

## 判据

每张 ticket 应有一个可检查的交付目标，能在单个 Execution Worktree 内实现、验证与交回；
所需前置产物明确为 dependency，不把跨票协同留成隐含条件。普通文件路径重叠本身不是拆票理由。

- **拆分：** 包含可独立验收的多个目标，或读取、实现和验证所需的同时在场上下文无法可靠承载时，
  沿交付物或依赖边界拆分，保留明确的验收与集成顺序。
- **合并：** 相邻细票没有独立验收价值、反复加载同一上下文且能在同一 Execution Worktree
  验证时合并；保留真实 dependency，已派发或被 claim 的票不由本 skill 自动重写。
